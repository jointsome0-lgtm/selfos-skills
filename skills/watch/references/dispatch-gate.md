# Post-verdict dispatch procedure

Load only when the [post-verdict policy check](../SKILL.md#post-verdict-dispatch-policy) identifies a dispatch requirement. Use its trusted policy, recorded base revision, and exact accepted verdict head.

1. Anchor to the exact verdict head. If the PR head has moved since the verdict, the verdict is stale — restart the watcher for the current head instead of dispatching.
2. Select the dispatch ref from the trusted policy, then run `gh workflow run <workflow-file> --repo <repo> --ref <dispatch-ref>` with its supplied inputs. By default, use the recorded base branch and commit. That workflow validates the verdict head through its inputs and reports its named check on the supplied SHA. Omitting `--ref` selects the default branch, which may differ from the PR's base.

   Use the PR head's workflow only when the caller or trusted base policy explicitly requires it and authorizes executing that workflow and checked-out code. A `GITHUB_SHA == expected_sha` assertion explains why a workflow needs the head revision; it does not grant authorization. PR-head policy cannot grant it either.

   Before dispatching a workflow from the PR head, use a policy-authorized immutable ref at the full verdict SHA, such as a protected tag. If the policy requires the literal head branch, keep that branch ref immutable until the dispatched run's SHA is recorded. Confirm that any PR code the workflow checks out is also pinned to the verdict SHA. Creating refs or changing protection needs existing caller or trusted-policy authorization; otherwise report the missing mechanism for owner resolution. A mutable branch followed by post-start cancellation is insufficient: unreviewed steps may already have executed. Record the verdict SHA as the expected dispatch commit while retaining the base revision used to select the policy.

   Confirm the workflow file exists at the selected ref. If a PR deletes the workflow that its policy requires running from the head branch, the current head cannot satisfy that gate. Report the contract gap for the owner to resolve; do not silently substitute the base workflow or waive the gate. GitHub also requires the workflow on the default branch for `workflow_dispatch`. If the workflow cannot be dispatched, fail closed unless the trusted policy supplies a working alternative trigger.

   A branch can move between selection and dispatch. Confirm the captured run's `headSha` equals the expected dispatch commit. If it differs, cancel the run. A moved base requires fresh policy evaluation; a moved PR head requires a fresh review. Repeat the gate only for the resulting accepted head and policy.
3. Watch the run just dispatched, not a check name: capture the created run's URL from the dispatch output when `gh` returns it; otherwise compare the workflow's run list from before and after the dispatch and fail closed unless exactly one new `workflow_dispatch` run appears — a nearby run started by another actor must never stand in for this one. Follow the captured run with `gh run watch <run-id> --repo <repo> --exit-status` — or, where the credential cannot use it (gh documents that fine-grained tokens cannot grant the `checks:read` it needs), track `gh run view <run-id> --repo <repo> --exit-status` until the run completes — and treat a nonzero exit as gate failure rather than reading success out of the human-readable output. `gh run watch` has no timeout of its own, so enforce the gate's patience mechanically around it (for example `timeout <remaining-seconds> gh run watch …`), treating expiry as gate failure. A pre-existing green check under the same name never satisfies the gate.
4. The gate is satisfied only when that dispatched run succeeds and the named check is reported green for the verdict head; then continue into the ordinary CI wait and merge. Green push-triggered checks alone, or a `no checks reported` result, never satisfy an active gate.
5. Fail closed, within a bounded patience: 30 minutes from dispatch by default, overridden by the caller argument `dispatch-timeout=<minutes>`. If the dispatch cannot be issued — including for missing Actions-write credentials — or the run fails, or the named check is not green for the verdict head when the patience expires, diagnose the failure under [CI and merge](../SKILL.md#ci-and-merge). Report a blocker if recovery needs unavailable access or changes outside the authorized scope. Never fall back to "push-triggered checks passed".

After every applicable gate passes, return to [CI and merge](../SKILL.md#ci-and-merge).
